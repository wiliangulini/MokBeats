## 13. Decisões técnicas tomadas

### Decisão 1: instalação do Node via `nvm`, não via `apt`/NodeSource

**Decisão:** usar `nvm install 24.18.1` (nvm já presente na VPS) em vez de substituir o pacote
`nodejs` do sistema.

**Justificativa:** o inventário revelou que a VPS é compartilhada — hospeda a
`floricultura-rosa-de-saron`, outra aplicação PM2, rodando sob o Node do sistema (v18.19.1, pacote
apt nativo do Ubuntu, não NodeSource). Substituir o Node global quebraria essa aplicação junto. A
própria VPS já tinha o precedente: a floricultura roda com `--interpreter` apontando para um Node
instalado via `nvm`, isolado do sistema.

**Alternativas consideradas:**
- NodeSource global via apt — descartada (afetaria a floricultura).
- Tarball manual em `/opt/node-24` — funcional, mas reinventa o que o `nvm` já presente resolve.

**Trade-offs:** nenhum — `nvm` já estava instalado e em uso comprovado nesta VPS especificamente
para este propósito.

### Decisão 2: correção de bug de `set -e` em `upload_audio()` (deploy-to-vps.sh)

**Decisão:** trocar `[ "$NO_AUDIO" = true ] && warn "..."` por um `if`/`fi` explícito antes do
`return`.

**Justificativa:** sob `set -e`, quando `[ "$NO_AUDIO" = true ]` avalia falso (caso padrão, sem
`--no-audio`), o `&&` nunca executa o `warn`, e o `return` bare (sem argumento) herda o status do
teste que falhou (1). Isso fez o script abortar silenciosamente logo após "Backend enviado",
pulando `configure_remote_env()` inteiro — sem nenhuma mensagem de erro visível. Reproduzido e
confirmado isoladamente com um script mínimo local antes da correção; a mesma reprodução, após a
correção (usando `if`/`fi` em vez de `&&`), retornou ao comportamento esperado. Bug pré-existente,
não introduzido por este lote — nunca se manifestara porque deploys anteriores aparentemente
sempre usaram `--no-audio` (o que faz o teste avaliar verdadeiro, evitando o caminho problemático).

**Alternativas consideradas:** nenhuma — é a forma idiomática correta para essa checagem sob
`set -e`.

**Trade-offs:** nenhum.

### Decisão 3: `return 0` explícito ao final de `validate_deploy()` e `show_summary()`

**Decisão:** adicionar `return 0` no fim de ambas as funções.

**Justificativa:** a execução real terminou com `EXIT_CODE=1` mesmo com todos os passos visíveis
bem-sucedidos (deploy completo, health check OK, banner final impresso). Investigação cuidadosa
(incluindo revisão da especificação POSIX para o exit status de blocos `if` sem `else` quando a
condição é falsa — que é 0, não o status do teste, ao contrário do que uma primeira leitura
sugeriria) não conseguiu isolar com certeza absoluta o mecanismo exato do `set -e` nesta shell
específica que produziu o `1` final. Diante da ambiguidade, e como o comportamento funcional real
foi confirmado por evidência direta e independente na VPS (não pelo exit code do script), a
correção aplicada é defensiva: garante que essas duas funções sempre retornem 0 explicitamente ao
alcançar seu fim normal, eliminando a ambiguidade independentemente da causa exata.

**Alternativas consideradas:** investigar mais a fundo o mecanismo exato — descartado por retorno
decrescente frente ao risco zero da correção defensiva.

**Trade-offs:** nenhum.

### Decisão 4: reconciliar IP/path em 4 documentos, não só os 2 originalmente previstos

**Decisão:** além de `server/DEPLOY_VPS.md` e `DEPLOY_CHECKLIST.md` (escopo original combinado com
o usuário), corrigir também `BUILD_AND_DEPLOY.md` e `CONFIG_APACHE_CORRETA.md`, onde o mesmo IP
antigo (`147.79.87.156`) e path antigo (`/var/www/mokbeats`) foram encontrados durante a varredura.

**Justificativa:** é o mesmo risco operacional (indução a deploy contra o servidor/path errado)
que motivou a correção original; encontrar e não corrigir teria deixado o problema pela metade.

**Alternativas consideradas:** manter escopo estrito nos 2 arquivos combinados — descartado por
deixar risco conhecido sem tratar.

**Trade-offs:** nenhum — substituição mecânica e literal (`sed`), sem alteração de conteúdo além do
IP/path.
